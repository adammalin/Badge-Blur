## Controlled model comparison

The earlier OWL-ViT release and the OWLv2 candidate were run locally against
the same five synthetic images using their respective tuned defaults.

- OWL-ViT produced counts `1, 3, 4, 1, 3`. Visual review found a duplicate
  partial mask in the event scene and only a partial mask on the large
  foreground badge.
- OWLv2 produced counts `1, 2, 4, 1, 3`. Visual review confirmed one complete
  box around each of the 11 visible badges.

The machine-readable CPU comparison and boxed overlays are generated by:

```bash
npm run benchmark:models
```

The browser WASM path was separately exercised because its confidence scores
are not numerically identical to the Node CPU path.

## Queue and pagination validation

The production build was opened from the local packaged server and the five
demo files were selected as a folder. Browser checks confirmed:

- page 1 renders four image cards and page 2 renders one;
- Previous/Next state and page labels update correctly;
- every retained review canvas has a maximum dimension of 1200 pixels;
- detection processes all five files sequentially and reaches 100%;
- the queue finishes with per-image counts `1, 2, 4, 1, 3`;
- changing pages releases the other page's previews; and
- full-resolution files are reopened one at a time for detection or export.

The bounded design prevents the application from decoding every
full-resolution source simultaneously. A representative soak test using
hundreds or thousands of cleared camera files remains required before
production deployment.

## Bulk export validation boundary

Version 0.7.0 uses the following bulk-export contract:

- one File System Access destination-folder selection;
- sequential writes into a unique
  `badge-remover-run-YYYYMMDD-HHMMSS-xxxxxxxx` folder;
- preserved source subfolders;
- unredacted originals are not copied into the run folder;
- no one-download-per-image fallback;
- `badge-removal-manifest.json` with initial and reviewed masks; and
- `badge-training-annotations.coco.json` for later offline model training.

The run-folder name contains both a timestamp and a UUID-derived suffix, and
the app checks for an existing directory before creation. A previous run
manifest can be imported with the original source folder to restore reviewed
masks and settings. Files are matched by relative path and byte size; changed
files are skipped.

## Format and metadata validation

Synthetic 8-bit fixtures were decoded, redacted, and re-read through the
packaged local runtime:

| Input | Output | Result |
| --- | --- | --- |
| JPEG | JPEG | Pass |
| PNG | PNG | Pass |
| TIFF (8-bit, one page) | TIFF | Pass |
| WebP | WebP | Pass |
| AVIF | AVIF | Pass |
| HEIC/HEIF | TIFF | Pass |

Synthetic Artist, XMP Description, and IPTC Keywords fields survived the
round trip in applicable formats. Output Orientation was normalized to
horizontal after pixel rotation. Each source also produced a MIE metadata
archive. A JPEG fixture containing an unredacted embedded thumbnail verified
that Artist metadata remained while `ThumbnailImage` was absent from both the
redacted output and MIE archive.

A generated 16-bit grayscale TIFF was rejected with the expected
greater-than-8-bit safety message and its Detect, Export copy, Detect all, and
Export all actions were disabled when it was the only selected file. This
prevents silent 16-to-8-bit reduction.

The packaged Apple-silicon 0.6.0 runtime separately passed HEIC preview,
HEIC-to-TIFF redaction, and metadata-archive API checks. The Windows archive
contains its native Sharp x64 module and vendored ExifTool executable, but
runtime execution still requires a Windows test PC.

## Four-corner and feather validation

A synthetic portrait was redacted with a deliberately tilted four-point mask
at feather settings 0%, 12%, and 25%. The rendered outputs confirmed:

- the affected region follows the quadrilateral rather than its rectangular
  bounding box;
- the pixelated content remains confined by the polygon alpha mask;
- increasing feather produces a progressively softer transition around the
  polygon; and
- metadata transfer still completes after polygon redaction.

The app UI exposes the Edge feather slider at its 10% default and explains the
four-corner workflow. Corner edits are accepted only while the quadrilateral
remains convex, preventing crossed or self-intersecting masks. Polygon points
are stored in the version 5 audit manifest and as COCO segmentation data.

## Automatic corner-fit validation

The edge fitter was run locally against the 11 frozen OWLv2 detections in the
five-image synthetic set:

| Image | Detected masks | Automatically fitted | Rectangle fallback |
| --- | ---: | ---: | ---: |
| `01-single-frontal-badge.png` | 1 | 1 | 0 |
| `02-two-person-event-badges.png` | 2 | 2 | 0 |
| `03-four-person-group-badges.png` | 4 | 4 | 0 |
| `04-outdoor-glare-motion-badge.png` | 1 | 0 | 1 |
| `05-low-light-multiscale-badges.png` | 3 | 3 | 0 |
| **Total** | **11** | **10** | **1** |

Visual overlay review confirmed that the 10 accepted quadrilaterals followed
the visible badge edges more closely than the original red bounding boxes.
Version 0.7.0 widened the supported tilt search and changed edge scoring to
sample the image gradient perpendicular to each candidate line with bilinear
interpolation. This corrected visibly tilted cases without changing the frozen
10-fit/1-fallback safety result.
The outdoor glare/motion badge produced a candidate that was too small and
correctly retained its rectangle. A same-sized control region without a badge
also failed the edge-continuity threshold and retained its rectangle.

For every accepted fit, the safety blend verified that the mask after the
configured 18% expansion still contained all four corners of the original
OWLv2 detection. This synthetic result validates the fitter/fallback behavior,
not production accuracy on cleared photography. Fit confidence, reason,
original detection bounds, polygon points, and user-adjustment state are
recorded in the version 5 manifest.

The corner-fit regression can be repeated locally with
`npm run test:corner-fit`. Run-folder collision and prior-run path-matching
checks can be repeated with `npm run test:run-storage`.

The automated in-app browser does not expose a controllable native directory
picker. A normal interactive Edge/Chrome destination choice and multi-file
write must therefore be rechecked on each target operating system.

## Platform validation boundary

Both platform packages are generated from the same `dist/`, model, demo files,
notices, and server source.

On the macOS build machine, validation covers archive integrity, model hash,
native Apple-silicon runtime, local server startup, security headers, and
byte-for-byte parity of shared package files. The Windows x64 package also
checks the pinned official Node runtime hash, PE architecture, launcher
structure, and CRLF line endings.

The Windows executable cannot run on the macOS build machine. Launch,
selection, inference, pagination, and bulk export remain pending on a managed
Windows 10 or Windows 11 x64 PC using Microsoft Edge or Google Chrome.
